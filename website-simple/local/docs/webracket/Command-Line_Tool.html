4 Command-Line Tool🔗

This chapter documents the current WebRacket command-line compiler. For installation and first-run walkthroughs, see the website Quick Start and Installation pages.

There are two ways the compiler can be invoked from the command line. Either as a direct shell command or as a raco subcommand.

  • webracket <arguments>

  • raco webracket <arguments>

In order to add the Racket launchers to your PATH environment variable, you can use DrRacket. In the menu "Help" choose the menu item "Configure Command Line for Racket".

The webracket command is installed as a "launcher" when the webracket package is installed. Alternatively, you can invoke the compiler as raco webracket. The two ways of invoking the compiler are equivalent.

The arguments for the webracket command are:

  • One source file plus optional flags (compile mode).

  • No source file together with --list-primitives (listing mode).

Use webracket --help or raco help webracket for a concise overview.

Use webracket --help-full or raco webracket --help-full for a complete reference.

4.1 Overview🔗

The overall goal is to compile a WebRacket source file, such as a #lang webracket/base module, to WebAssembly.

The "reusable runtime" is program independent and can be used by multiple programs.

By default, WebRacket writes a small set of files that work together: a program .wasm file, a reusable runtime .wasm file, and a generated host file. Programs that use direct JavaScript FFI wrappers also get a reusable FFI .wasm file.

  • Node mode: a .js host file that loads and runs the program and runtime Wasm modules in the terminal.

  • Browser mode: a .html host file that loads and runs the program and runtime Wasm modules in the browser.

So the normal output is a small set of files that work together.

To keep source directories tidy, use --dest <dir> to write the generated files to a separate directory:

webracket --browser --dest generated program.rkt
webracket --browser --dest generated program.rkt

4.2 Quick Start (CLI)🔗

Minimal compile:

webracket --node program.rkt
webracket --node program.rkt

Compile and run immediately in Node mode:

webracket --node --run program.rkt
webracket --node --run program.rkt

In most cases, you will want to use --dest generated as well.

4.3 Common Tasks🔗

Compile with default output names:

webracket --node program.rkt
webracket --node program.rkt

Choose explicit output files:

webracket --node --wat-file out/program.wat --wasm-file out/program.wasm --host-file out/program.js program.rkt
webracket --node --wat-file out/program.wat --wasm-file out/program.wasm --host-file out/program.js program.rkt

Choose a destination directory for the default outputs:

webracket --node --dest out program.rkt
webracket --node --dest out program.rkt

Explicit --wat-file, --wasm-file, and --host-file options still take precedence over --dest.

Target browser host generation:

webracket --browser program.rkt
webracket --browser program.rkt

Browser output must be served over HTTP. In most cases, you will want to use a local web server during development. If you attempt to open the host .html file directly, the browser security policy will block the loading of the WebAssembly files.

The console bridge installs a global object WR in the JavaScript environment. You can use this to inspect and call exposed WebRacket bindings from the JavaScript console. This is mainly useful while debugging.

Target browser host generation with the browser console bridge enabled:

webracket --browser --console-bridge program.rkt
webracket --browser --console-bridge program.rkt

4.4 Compiler Debugging🔗

Dump compiler passes (limit to 25 dumps):

webracket --node --dump-passes tmp/passes --dump-passes-limit 25 program.rkt
webracket --node --dump-passes tmp/passes --dump-passes-limit 25 program.rkt

Print timing information:

webracket --node --timings program.rkt
webracket --node --timings program.rkt

Write pretty-formatted WAT (default is a single line):

webracket --node --pretty-wat program.rkt
webracket --node --pretty-wat program.rkt

Print all known primitives:

webracket --list-primitives
webracket --list-primitives

4.5 Output Files And Defaults🔗

For input program.rkt, default outputs are:

  • program.wat: Text-form WebAssembly for the program module. Useful for inspection and debugging.

  • program.wasm: Binary WebAssembly for the program module, produced from program.wat.

  • webracket-runtime-<fingerprint>.wasm: Reusable runtime module. The fingerprint is stable for identical runtime contents, so multiple programs can share the same runtime file.

  • webracket-ffi-<fingerprint>.wasm: Optional reusable FFI module, emitted when direct JavaScript FFI wrappers are active.

  • program.wasm.map.sexp: Label-map metadata used to map generated code labels back to source-oriented information.

  • program.js (Node mode default): Host support file that loads the program module and any reusable runtime/FFI modules, then provides the environment needed to run in Node.js.

  • program.html (browser mode default): Host support file that loads the program module and any reusable runtime/FFI modules, then provides the environment needed to run in a browser.

4.6 Complete Option Reference🔗

Run behavior:

  • -r / --run: Run the compiled program after generation (Node mode only).

Target selection (mutually exclusive):

  • -n / --node: Generate Node host output (default).

  • -b / --browser: Generate browser host output.

Output path options:

  • --wat-file <path>: Explicit program WAT output path.

  • --wasm-file <path>: Explicit program WASM output path.

  • --host-file <path>: Explicit generated host output path.

  • --dest <dir>: Write the default outputs under <dir>.

Debug and inspection options:

  • -v / --verbose: Verbose compiler messages.

  • --list-primitives: Print sorted primitive names and exit.

  • --console-bridge: In browser mode, install globalThis.WR so the browser console can inspect and call exposed WebRacket bindings.

  • --no-console-bridge: Disable the browser console bridge (default).

  • --label-map-forms: Include heavyweight source form payloads in .wasm.map.sexp.

  • --no-label-map-forms: Omit source form payloads in .wasm.map.sexp (default).

  • --dump-passes <dir>: Write per-pass dumps to <dir>.

  • --dump-passes-limit <n>: Limit pass dumps; 0 means no dumps.

  • --timings: Print timing breakdown for compilation stages.

  • --no-pretty-wat: Write .wat without pretty formatting (default).

  • --pretty-wat: Write .wat with pretty formatting.

Virtual filesystem options:

  • --vfs-file VFS=PATH: Preload a Node host file into a VFS file.

  • --vfs-url VFS=URL: Fetch a URL into a VFS file.

  • --vfs-text VFS=TEXT: Embed inline text as a VFS file.

  • --vfs-base64 VFS=BASE64: Embed small inline base64 bytes as a VFS file.

  • --vfs-mkdir VFS: Create an empty VFS directory.

  • --vfs-dir VFS=PATH: Preload a Node host directory into a VFS directory.

  • --vfs-tar-file VFS=PATH: Mount a Node host tar archive as a read-only VFS subtree.

  • --vfs-tar-url VFS=URL: Mount a tar archive fetched by URL as a read-only VFS subtree.

Sources ending in .tar.gz or .tgz are treated as gzip-compressed tar archives. For a tutorial and compatibility notes, see Files and the Virtual Filesystem.

4.7 Legacy Standard Library And Manual FFI🔗

Most module-based programs should use require forms in the source module instead of manual standard-library or .ffi command-line flags. The following options remain available for legacy inputs and diagnostics.

Legacy standard library inclusion:

  • --stdlib: Include the legacy standard library.

  • --no-stdlib: Do not include the legacy standard library (default).

Manual FFI:

  • --ffi <file>: Add an .ffi input file; may be repeated.

Legacy examples:

  • webracket --node --stdlib program.rkt

  • webracket --node --ffi dom --ffi standard program.rkt

  • webracket --list-primitives --ffi dom --ffi standard

4.8 Internal And Advanced Options🔗

These options are mainly for compiler development, module-bridge debugging, performance investigation, and staged-provider experiments. They are useful when reducing WebRacket bugs, but ordinary programs usually should not need them.

Assembler environment options:

  • --exec-path-from-shell: Import PATH and MANPATH from the login shell before finding wasm-tools (default).

  • --no-exec-path-from-shell: Use the current process environment when finding wasm-tools. This is useful for tests and CI environments that already provide the desired PATH.

Module and provider options:

  • --webracket-module-bridge: Force #lang webracket/base or #lang webracket/full through the module bridge.

  • --provider-substitutions: Enable Goal 1 provider substitutions (default).

  • --no-provider-substitutions: Disable Goal 1 provider substitutions for diagnostics.

  • --provider-cache-dir <dir>: Use <dir> for provider-slice caches.

  • --provider-cache-report: Print provider-cache entries and exit.

  • --clear-provider-cache: Delete the provider cache directory before compiling.

  • --force-provider-cache-refresh: Regenerate provider cache artifacts even when fingerprints match.

Staged provider options:

  • --io-format-provider: Compose the staged original-Racket io/format provider.

  • --no-io-format-provider: Disable the staged io/format provider for debugging.

  • --expander-read-provider: Compose the staged original-Racket expander/read provider. This is needed by programs that use datum read.

  • --no-expander-read-provider: Disable the staged expander/read provider (default).

  • --expander-read-syntax-provider: Compose the private staged original-Racket read-syntax provider.

  • --no-expander-read-syntax-provider: Disable the private staged read-syntax provider (default).

Runtime output options:

  • --split-runtime: Emit separate program and runtime Wasm modules (default).

  • --no-split-runtime: Emit one monolithic Wasm module.

  • --split-runtime-cache-reference: In Node split-runtime mode, read the stable runtime Wasm directly from the runtime cache. This requires the cache to be prewarmed.

  • --no-split-runtime-cache-reference: Write the content-addressed runtime Wasm file next to the program output (default).

  • --split-runtime-core-url <url>: In browser split-runtime mode, fetch a prewarmed runtime Wasm file from <url> instead of writing a local runtime file.

  • --no-split-runtime-core-url: Write the browser runtime Wasm file next to the program output (default).

  • --split-runtime-core-only: Split only registered core-runtime helpers into the runtime module.

  • --no-split-runtime-core-only: Use the classified runtime/program split strategy (default).

  • --split-runtime-provider-runtime: For module-language input, merge cached module-bridge provider fragments into the runtime module.

  • --no-split-runtime-provider-runtime: Keep module-bridge provider fragments in the program module (default).

  • --split-runtime-ffi-module: Explicitly emit active direct FFI wrappers as a separate FFI Wasm module. This is the default in compatible split-runtime modes when FFI wrappers are active.

  • --no-split-runtime-ffi-module: Keep active direct FFI wrappers in the program module.

Experimental compiler options:

  • --alpha-rename-profile: Print alpha-rename/pass1 counters and helper timings.

  • --simplify-profile: Print simplify-LFE rule and shape diagnostics.

  • --enable-cc-analysis: Enable the new closure-conversion analysis.

  • --enable-simplify: Run the early simplify-LFE pass.

  • --frontend-cache: Cache serialized post-unexpand frontend syntax in the project provider cache. This is experimental and opt-in.

  • --no-frontend-cache: Disable frontend syntax caching (default).

  • --module-bridge-elide-public-cells: Expose safe module-bridge public exports as plain values.

  • --tree-shake: Tree-shake runtime primitives (default).

  • --no-tree-shake: Do not tree-shake runtime primitives.

  • --tree-shake-report <file>: Write the runtime primitive report to <file>.

  • --letrec-basic: Use the basic letrec lowering strategy.

  • --letrec-waddell: Use the Waddell letrec lowering strategy.

  • --letrec-scc: Use the SCC letrec lowering strategy (default).

  • --print-top-level-results: Print each top-level expression result with print.

  • --list-provider-slices: Print original-Racket provider slices and exit.

Local server options:

The local compile server reduces compiler startup costs by keeping one Racket process warm across repeated compiles. It is especially useful with prewarmed split-runtime caches, where the user program can avoid both rebuilding the shared runtime and reloading the compiler process. Starting the server does not by itself route compiles through it; set WEBRACKET_COMPILE_SERVER=1 to route ordinary compile commands through the server. Server state defaults to a checkout-local "tmp/webracket-compile-server-..." directory; set WEBRACKET_COMPILE_SERVER_STATE_DIR to choose a different location.

  • --server-start: Run the local compile server in the foreground.

  • --server-status: Print local compile server status and exit.

  • --server-stop: Stop the local compile server and exit.

  • webracket --browser --expander-read-provider program.rkt

4.10 Operational Constraints🔗

  • --run cannot be used together with --browser.

  • Compile mode requires exactly one source filename.

  • Listing mode (--list-primitives) requires no source filename.

  • When using --run in Node mode, a working node executable with WebAssembly exnref support is required.

  • A working wasm-tools installation is required for WAT-to-WASM assembly.

  • Output paths must be distinct: the program WAT, program WASM, label-map, and host output files cannot collide.

  • Output locations must be writable.

  • --dump-passes-limit <n> requires an exact nonnegative integer.

See Installation for Node version guidance. Current Node 24 LTS and Node 26 enable WebAssembly exnref by default; older supported Node lines may require --experimental-wasm-exnref.
