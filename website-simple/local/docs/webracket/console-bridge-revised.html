9 The Browser Console Bridge - Revised🔗

The browser console bridge is an opt-in debugging helper for generated browser pages. When enabled, the page installs globalThis.WR, a small JavaScript entry point that can look up selected WebRacket bindings, call selected WebRacket functions, and list the names available to the bridge.

It is useful while developing browser examples because it lets you inspect a running WebRacket page from DevTools without adding temporary logging and rebuilding for every small question.

It is not a general Racket evaluator. Calls such as WR("counter") look up a binding named counter; they do not read and evaluate Racket source text.

9.1 Enable The Bridge🔗

Compile a browser program with --console-bridge. Use --dest to keep generated files in one directory:

webracket --browser --console-bridge --dest generated counter.rkt
webracket --browser --console-bridge --dest generated counter.rkt

This writes files such as generated/counter.html and generated/counter.wasm. Serve the directory that contains the generated output, open the page in a browser, and then open DevTools.

If the bridge was installed successfully, the browser console can use WR:

WR.help()

WR.names()

9.2 Small Example🔗

"counter.rkt"

#lang webracket/base

 

(define counter 0)

 

(define (increment! amount)

  (set! counter (+ counter amount))

  counter)

 

(define (current-counter)

  counter)

 

(display "counter page ready")

Compile it:

webracket --browser --console-bridge --dest generated counter.rkt
webracket --browser --console-bridge --dest generated counter.rkt

Serve the project directory, then open generated/counter.html. In the browser console:

> WR("counter")

0

> WR("increment!", 5)

5

> WR.call("current-counter")

5

There is also a checked-in example at "examples/console-bridge/console-bridge.rkt".

9.3 What WR Does🔗

The bridge exposes a JavaScript function named WR. Its common operations are:

  • WR(name) looks up a binding and prints the WebRacket result.

  • WR(name, ...args) calls a binding as a function.

  • WR.call(name, ...args) always performs a function call, even with zero arguments.

  • WR.value(name, ...args) returns the converted JavaScript value without automatic console printing.

  • WR.raw(name, ...args) returns the full result object.

  • WR.names() lists exposed names.

  • WR.search(query) searches exposed names.

  • WR.namesDetailed() lists exposed names with metadata.

  • WR.write(name, ...args) prints the WebRacket representation.

  • WR.print(name, ...args) uses JavaScript console inspection for the converted value.

  • WR.format(value) formats a JavaScript value with WebRacket’s printer.

  • WR.help() prints a usage summary.

9.4 Lookup Versus Call🔗

The convenience function WR chooses between lookup and call based on the number of arguments.

  • WR("current-counter") looks up the function value.

  • WR.call("current-counter") calls the zero-argument function.

  • WR("increment!", 1) calls increment! with one argument.

Use WR.call when you want the intent to be unambiguous.

9.5 Result Objects🔗

Use WR.raw when you need to distinguish successful lookups from failures. A typical successful result looks like this:

> WR.raw("counter")

{

  ok: true,

  kind: "value",

  value: 5,

  printed: "5",

  error: "",

  message: "",

  operation: "ref",

  name: "counter",

  args: []

}

A missing binding returns a structured failure instead of pretending that the lookup succeeded:

> WR.raw("does-not-exist")

{

  ok: false,

  kind: "missing-binding",

  value: false,

  printed: "",

  error: "...",

  message: "...",

  operation: "ref",

  name: "does-not-exist",

  args: []

}

9.6 Values Across The Boundary🔗

When WR returns a value, WebRacket converts it to a JavaScript value where possible. For example:

  • fixnums and flonums become JavaScript numbers;

  • strings become JavaScript strings;

  • vectors become JavaScript arrays;

  • booleans become JavaScript booleans;

The result object also keeps printed, a WebRacket-style representation of the value, which is often easier to read when debugging Racket data.

9.7 Which Names Are Exposed🔗

The bridge exposes top-level bindings from the compiled browser program. That includes definitions from your source file and some bindings that are present because the compiled program uses them.

Local variables are not exposed. In this example, counter and increment! may be visible through WR, but temporary is not:

"example.rkt"

#lang webracket/base

 

(define counter 0)

 

(define (increment! amount)

  (let ([temporary (* amount 2)])

    (set! counter (+ counter temporary))

    counter))

Use WR.names() and WR.namesDetailed() to see what the generated page actually exposes.

9.8 When To Use It🔗

Use the console bridge when you want to inspect or poke at a running browser page during development.

It is less appropriate when:

  • you need a general REPL for arbitrary Racket expressions;

  • you want a stable application API for JavaScript code;

  • you do not want the page to publish debugging hooks globally.

Because it installs a global debugging helper, the bridge is disabled by default.

9.9 Troubleshooting🔗

If WR is missing in the browser console, check these first:

  • Was the page compiled with --console-bridge?

  • Did the page finish loading? Try WR.help() after the page is ready.

  • Are you serving the generated files you just built?

  • Did the browser load the generated .wasm file successfully?

If a lookup fails, start with:

WR.raw("name-you-expect")

WR.names()

WR.namesDetailed()

Those calls usually tell you whether the name is missing, spelled differently, or present because it came from generated support code.
