6 WebRacket for Racket Programmers🔗

This chapter describes WebRacket from the perspective of a programmer familiar with Racket.

6.1 Overview🔗

It is also possible to run WebRacket programs in Node.js.

WebRacket lets you write programs in Racket and run them in the browser. It uses Racket as a frontend language, but executes programs on a custom runtime compiled to WebAssembly.

  • Programs are written in Racket syntax.

  • They are expanded using the Racket expander.

  • They are compiled to WebAssembly and run in the browser.

The main differences from Racket arise from the runtime environment and the constraints of WebAssembly and the browser.

6.2 The Compilation Pipeline🔗

A WebRacket program is processed in several stages:

  • The source file is read into syntax objects.

  • The program is expanded using the Racket expander.

  • The expanded program is compiled to WebAssembly text (WAT) for the program module.

  • The program WAT is assembled into a WebAssembly module (.wasm); split-runtime output also uses reusable runtime and FFI modules.

  • A small host file (HTML or JavaScript) is generated.

The use of the Racket expander means that macros and special forms work like they do in Racket.

6.3 What is the same🔗

Many core aspects of Racket are preserved:

  • The Racket expander is used, so macros work.

  • Core forms such as lambda, if, let, match, and for are supported.

  • Tail calls and multiple values are supported.

  • Data structures such as pairs, vectors, strings, symbols, and mutable hash tables are available.

  • Structures work. THis includes super-structures and structure properties.

In practice, many programs written using racket/base can be adapted to WebRacket with relatively small changes.

Since the Racket expander is used at compilation time, anything compile time related (phase 1 and greater) is using normal Racket. This means you can use syntax-parse for macros.

6.4 What is different🔗

WebRacket programs do not run on Racket’s usual runtime system. Instead, they are compiled to WebAssembly and executed on a custom runtime inside the browser.

This leads to several differences:

  • No modules (yet): Programs are written as top-level code. Module support is under development.

  • No continuations: Features such as call/cc and continuation marks are not available.

  • Single-threaded execution: There are no threads or places. Programs run in a single browser thread.

  • Numeric limitations: Numbers are currently limited to fixnums and flonums.

  • Keyword arguments: The forms define and lambda does not support keyword arguments. For programs that need keyword arguments, look at the (include-lib define) library.

  • Different I/O model:

    Programs can print to the JavaScript console.

    There is no terminal. Programs do not print to a console by default; instead, they typically produce visible results in the browser.

6.5 Programs Without Modules🔗

WebRacket programs are currently written as a single top-level program. There is no module form, and no separate compilation units.

Instead, the entire program is treated as one sequence of top-level definitions and expressions.

6.5.1 One big top-level🔗

A WebRacket source file is read and wrapped in a single begin before compilation. For example:

(define (f x) (+ x 1))
(define (g x) (f (* x 2)))
 
(g 10)

is treated as one top-level program, where all definitions are visible to each other.

This means:

  • Definitions are processed in order.

  • All bindings live in the same global scope.

  • There is no module-level encapsulation.

For simple programs, this is often sufficient. For larger programs, it requires a different organization style than in Racket.

6.5.2 Using libraries with include-lib🔗

To structure programs and reuse code, WebRacket provides the include-lib form.

(include-lib web-easy)
(include-lib define)

This form inserts the contents of a library into the current program at compile time.

Conceptually, it is similar to copying the contents of the library into your file before compilation.

6.5.3 Standard libraries🔗

WebRacket provides a collection of libraries that can be included using include-lib. These libraries provide functionality that would normally be imported via modules in Racket.

Examples include:

  • (include-lib web-easy) for building user interfaces

  • (include-lib define) for extended define and lambda forms

  • Libraries for DOM access, events, and browser APIs

Because there is no module system, libraries are designed to work in a single shared namespace.

6.5.4 Program organization🔗

Without modules, programs are typically organized by:

  • Splitting code into multiple files and including them with include-lib or similar mechanisms

  • Grouping related definitions together

  • Using naming conventions to avoid conflicts

Although this is different from standard Racket practice, it is often sufficient for the kinds of interactive programs WebRacket targets.

6.5.5 Summary🔗

In WebRacket:

  • Programs are single top-level units.

  • There is no module system (yet).

  • Libraries are included using include-lib.

This model keeps the compilation process simple, while still allowing code reuse through libraries.

6.6 The Runtime Model🔗

WebRacket uses a custom runtime implemented in WebAssembly.

  • Values are represented using WebAssembly GC types.

  • Heap-allocated values such as pairs, strings, and vectors are implemented as WebAssembly structures.

  • Closures are explicit runtime objects.

6.7 Interacting with the Browser🔗

WebRacket programs run inside a browser environment.

Interaction with the browser is explicit and happens through:

  • Libraries such as web-easy for building user interfaces.

  • Bindings to DOM and Web APIs.

  • The JavaScript foreign-function interface (FFI).

Because WebAssembly is separate from JavaScript, all interaction between WebAssembly goes through a JavaScript ↔ WebAssembly value conversion bridge.

6.8 Program Structure🔗

WebRacket programs are typically structured differently from traditional Racket programs.

Instead of computing a value and exiting, a program usually:

  • constructs a user interface

  • inserts it into the page

  • responds to events over time

Programs are therefore:

  • interactive

  • event-driven

  • long-running

6.9 Summary🔗

For a Racket programmer, WebRacket can be understood as:

  • Racket syntax and macros

  • compiled to WebAssembly

  • running on a custom runtime in the browser

  • with explicit access to browser APIs
