8 The Browser Console Bridge🔗

The browser console bridge lets a generated browser page expose selected WebRacket bindings to the browser’s JavaScript console.

In practice, it gives you a small helper named WR in the page. You can then use the browser console to:

  • look up a top-level WebRacket variable

  • call a top-level WebRacket function

  • inspect which names are available

  • debug a running page without editing the source file first

This chapter explains what the bridge is, what it is for, how to enable it, and how to use it from the browser console.

8.1 What It Is🔗

Normally, a WebRacket program runs inside WebAssembly, and the browser console runs JavaScript.

Those are two different worlds:

  • your WebRacket definitions live inside the compiled WebAssembly program

  • the browser console can only see ordinary JavaScript values

The console bridge is a small browser-side helper that connects those two worlds.

When the bridge is enabled, WebRacket installs a function named globalThis.WR. In the browser console, that means you can write:

WR("x")

WR("add1*", 41)

WR.call("current-counter")

WR.search("display")

WR.help()

WR.names()

and the page asks the running WebRacket program to look up or call the corresponding binding.

8.2 What It Is For🔗

The console bridge is mainly a debugging and exploration tool.

It is useful when you want to:

  • check the current value of a top-level variable

  • call a helper function in a running page

  • see whether a name from your program or the standard library is available

  • experiment from the console while developing browser code

It is not a general-purpose evaluator for arbitrary Racket source text.

For example, this works:

WR("counter")

WR("increment!", 1)

But this does not mean “evaluate a Racket expression from a string”:

WR("(+ 1 2)")

That string is treated as a binding name, not as source code to read and evaluate.

8.3 How To Enable It🔗

The bridge is off by default.

To enable it, compile your browser program with --console-bridge:

webracket --browser --console-bridge counter.rkt
webracket --browser --console-bridge counter.rkt

This generates the usual browser output files, such as:

  • counter.html

  • counter.wasm

When you open counter.html in a browser, the page installs WR in the browser console.

8.4 Complete Example🔗

Here is a small complete example:

"counter.rkt"

(define counter 0)

 

(define (increment! amount)

  (set! counter (+ counter amount))

  counter)

 

(define (current-counter)

  counter)

 

(display "counter page ready")

There is also a checked-in example in the repository:

  • "examples/console-bridge/console-bridge.rkt"

Compile it:

webracket --browser --console-bridge counter.rkt
webracket --browser --console-bridge counter.rkt

Serve the generated files from the directory where they were written:

raco static-web
raco static-web

Then open the URL printed by raco static-web in your browser and visit counter.html.

Open Developer Tools and switch to the Console tab.

At that point, the page is running and the console bridge is available.

8.5 Opening The Browser Console🔗

If you have not used the browser console before, the general pattern is:

  • open the generated page in your browser

  • open Developer Tools

  • choose the Console tab

  • type calls such as WR("counter") and press Enter

In Chrome and other Chromium-based browsers, common shortcuts are:

  • F12

  • Ctrl+Shift+I on Windows and Linux

  • Cmd+Option+I on macOS

If the page is open but WR is missing, the usual cause is that the program was compiled without --console-bridge.

8.6 Console Session🔗

Here is an example of what a browser console session can look like.

Look up a variable:

> WR("counter")

0

Call a function:

> WR("increment!", 5)

5

Read the variable again:

> WR("counter")

5

Call a zero-argument function explicitly:

> WR.call("current-counter")

5

Ask for a quick reminder:

> WR.help()

WebRacket console bridge

  WR(name, ...args)        Look up or call a binding and print the WebRacket result.

  WR.value(name, ...args)  Return the converted JavaScript value without printing.

  ...

List the exposed names:

> WR.names()

["counter", "current-counter", "display", "increment!", ...]

Search the exposed names:

> WR.search("count")

["counter", "current-counter"]

Show richer binding metadata:

> WR.namesDetailed()

[

  { name: "counter", origin: "program", mutable: true, kind: "top-level", source: "/.../counter.rkt" },

  { name: "display", origin: "stdlib", mutable: false, kind: "top-level", source: "/.../stdlib/..." },

  ...

]

Read a value without printing it first:

> WR.value("counter")

5

Print the WebRacket representation explicitly:

> WR.write("counter")

5

Inspect the converted JavaScript value directly:

> WR.print("counter")

5

Inspect the full result object:

> WR.raw("counter")

{

  ok: true,

  kind: "value",

  value: 5,

  printed: "5",

  error: "",

  message: "",

  operation: "ref",

  name: "counter",

  args: []

}

Try a missing name:

> WR.raw("does-not-exist")

{

  ok: false,

  kind: "missing-binding",

  value: false,

  printed: "",

  error: "...",

  message: "...",

  operation: "ref",

  name: "does-not-exist",

  args: []

}

Format a JavaScript value with the WebRacket formatter:

> WR.format(["bridge", 7])

"(bridge 7)"

The exact formatting of objects in the console depends on the browser, but the overall shape is the same.

8.7 Console Bridge Operations🔗

When the bridge is enabled, the browser page installs several console bridge entry points:

8.7.1 WR(name, ...args)🔗

This is the main convenience form.

If you give it just a name, it looks up that binding, prints the result to the console in WebRacket style, and returns a JavaScript value.

If you give it a name plus extra arguments, it treats the named binding as a function, calls it, prints the result, and returns the converted JavaScript value.

Examples:

WR("counter")

WR("increment!", 1)

8.7.2 WR.value(name, ...args)🔗

This is the same lookup or call, but without the automatic console printing.

Use it when you only want the returned JavaScript value.

Example:

const n = WR.value("counter");

8.7.3 WR.call(name, ...args)🔗

This always performs a function call, even when you do not supply any arguments.

That is useful for a zero-argument function, because:

  • WR("current-counter") looks up the binding

  • WR.call("current-counter") invokes the function

Example:

WR.call("current-counter")

8.7.4 WR.raw(name, ...args)🔗

This returns a richer result object that shows whether the operation succeeded.

It is useful for debugging failures or distinguishing a missing binding from a successful call.

Typical fields are:

  • ok: whether the operation succeeded

  • kind: a short result tag such as \"value\" or \"missing-binding\"

  • value: the JavaScript value, when conversion succeeded

  • printed: the WebRacket-style printed form

  • error: error information when the operation failed

  • message: the same failure in a form suitable for throwing as a JavaScript Error

  • operation: \"ref\" for lookup or \"call\" for a function call

  • name and args: the original bridge request

8.7.5 WR.names()🔗

This returns a JavaScript array of the names that the bridge exposes for the current page.

Use it when you are not sure which bindings are available.

8.7.6 WR.search(query)🔗

This searches the exposed binding names using a case-insensitive substring match.

Use it when:

  • you remember part of a name but not the whole name

  • WR.names() returns too many bindings to scan comfortably

Example:

WR.search("display")

WR.search("ADD1")

8.7.7 WR.namesDetailed()🔗

This returns a JavaScript array of objects with a little more context for each exposed binding.

Typical fields are:

  • name: the binding name

  • origin: where the binding came from, such as \"program\" or \"stdlib\"

  • mutable: whether the top-level binding is mutable

  • kind: currently \"top-level\"

  • source: the source path when available

Use it when WR.names() is too flat and you want to understand why a binding is present.

8.7.8 WR.write(name, ...args)🔗

This behaves like WR(name, ...args), but it makes the intent explicit: print the WebRacket representation and return the converted JavaScript value.

8.7.9 WR.print(name, ...args)🔗

This also looks up or calls a binding, but it uses JavaScript console inspection for the converted value instead of the WebRacket printed representation.

It is most useful for vectors, arrays, and structured data that you want to expand directly in DevTools.

8.7.10 WR.help()🔗

This prints a short usage summary in the console and returns that same text as a JavaScript string.

8.7.11 WR.format(value)🔗

This sends an ordinary JavaScript value through the bridge and asks WebRacket to format it.

It is handy when you want to compare:

  • the JavaScript console view of a value

  • the WebRacket printed view of the same value

8.8 How Values Cross The Boundary🔗

The console bridge sits between:

  • WebRacket values inside WebAssembly

  • JavaScript values in the browser console

When you call WR, WebRacket converts the result to a form that the browser host can understand, and then the browser host converts that to an ordinary JavaScript value.

So, for example:

  • a WebRacket fixnum becomes a JavaScript number

  • a WebRacket string becomes a JavaScript string

  • a WebRacket vector becomes a JavaScript array

  • a missing binding becomes a structured error result

The bridge also keeps a printed WebRacket-style representation so the console output is easier to read while debugging.

8.9 What Names Are Exposed🔗

The bridge exposes top-level bindings from the compiled browser program.

In practice, that means names such as:

  • definitions from your source file

  • top-level bindings brought in by the standard library that are part of the compiled program

Local variables are not exposed.

So if you write:

"example.rkt"

(define counter 0)

 

(define (increment! amount)

  (let ([temporary (* amount 2)])

    (set! counter (+ counter temporary))

    counter))

then counter and increment! may be available through WR, but temporary is not.

8.10 When To Use It🔗

The console bridge is a good fit when:

  • you are developing a browser page and want quick inspection from DevTools

  • you want to test a helper without recompiling for each tiny change

  • you want to understand the state of a running WebRacket page

It is less appropriate when:

  • you need a general REPL for arbitrary Racket expressions

  • you want to expose an application API to ordinary page JavaScript in production

  • you do not want the page to publish debugging hooks globally

Because of that last point, the bridge is opt-in and disabled by default.

8.11 Troubleshooting🔗

If WR is missing in the browser console, check these common causes:

  • The page was compiled without --console-bridge.

  • The page has not finished loading yet. Wait for the page to start, then try again.

  • You are serving an older generated .html or .wasm file than the one you just built.

  • The browser page failed to load the generated .wasm file, so the runtime never finished installing the bridge.

When the bridge is enabled successfully, the browser console prints a short banner telling you to try WR.help() or WR.names().

If a lookup fails, start with:

WR.raw("name-you-expect")

WR.names()

WR.namesDetailed()

That usually tells you whether:

  • the name is missing entirely

  • the binding exists under a different spelling

  • the binding came from your program or from the standard library
