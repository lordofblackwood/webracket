59 WebRacket at a Glance🔗

This is a high-level overview of WebRacket.

59.1 What is WebRacket?🔗

WebRacket is a Racket-to-WebAssembly compiler and runtime designed to run practical Racket programs directly in the browser.

It compiles a substantial subset of Racket to WebAssembly, which you can think of as portable machine code for the browser.

WebAssembly runs in a virtual machine that is separate from the JavaScript engine. Because of this separation, a foreign-function interface (FFI) is required when WebRacket code needs browser features such as DOM operations, timers, and graphics APIs.

In practice, WebRacket:

  • Targets modern browsers such as Chrome, Firefox, and Safari.

  • Uses a custom runtime designed for WebAssembly.

  • Keeps the boundary to JavaScript explicit via the FFI.

59.2 What WebRacket is not🔗

WebRacket is not a drop-in replacement for Racket on the Racket VM. Some features are missing or behave differently because of browser and WebAssembly constraints.

WebRacket aims for a useful and predictable subset, with differences reduced over time.

59.3 Execution Model🔗

WebRacket programs execute as single-threaded WebAssembly modules embedded in a browser environment. This model drives how computation, memory management, and host interaction are structured.

  • Single-threaded execution: no parallel threads or shared-memory concurrency.

  • Custom runtime: implements core Racket value representations and primitive operations.

  • WebAssembly GC types: uses Wasm GC for heap-allocated values.

59.4 Language Coverage🔗

WebRacket focuses on practical web programs. It supports many core forms and data structures. Some areas are still a work in progress; see Implemented Primitives for the current primitive list.

Supported areas include:

  • Fixnums and flonums.

  • Strings and byte strings.

  • Symbols and keywords.

  • Pairs, vectors, boxes, and mutable hash tables.

  • The standard expander, including for and match.

  • Tail calls, multiple values, and upward exceptions.

  • Structures with super-structures and properties.

  • Large parts of racket/base.

Current limitations include:

  • Single-threaded execution only.

  • Module support is still in progress.

  • No support for continuations and continuation marks.

  • Some numeric and control features are not yet implemented.

  • Keyword-argument behavior is evolving; see the Libraries chapter for define/key.

59.5 JavaScript FFI🔗

WebAssembly programs can’t directly call JavaScript functions. A foreign-function interface (FFI) is needed as a bridge between the two languages.

Only very simple values, such as integers and floating-point numbers, can be passed directly when a JavaScript function is called from WebAssembly. To pass other values, WebAssembly needs to encode the values as bytes and store them in a shared byte array. On the JavaScript side, the bytes are decoded before the function is invoked. This process is called FASL encoding and decoding.

The process is similar when JavaScript calls a WebAssembly function.

WebRacket attempts to automate this process as much as possible, but you still need to be aware that not all values can cross the bridge.

For common browser APIs, WebRacket has efficient static bindings. This covers the DOM, Canvas, and libraries such as MathJax, Xterm.js, and JSXGraph.

If you need other browser APIs, there is a dynamic FFI available.
