5 Files and the Virtual Filesystem🔗

WebRacket programs can use many familiar Racket file, path, and port operations. Since a WebRacket program may run in a browser, it cannot assume that the host has a normal operating-system filesystem available to the compiled program. Instead, WebRacket provides a virtual filesystem, or VFS.

The VFS is an in-memory filesystem seen by the WebRacket program. Host files, URLs, inline data, directories, and tar archives can be loaded into VFS paths. After that, the program works with those VFS paths using ordinary Racket-style operations such as file->string, open-input-file, directory-list, and copy-file.

5.1 The Basic Idea🔗

The goal is for WebRacket programs to use files in the usual Racket way. A program should be able to open /app/config.txt, read bytes from it, list a directory, or write a result file without caring whether it is running under Node or in a browser.

The browser is the reason a VFS is needed. Browser programs do not have direct access to an operating-system filesystem. A browser page cannot simply open an arbitrary local file path such as /Users/alice/config.txt. Instead, WebRacket starts with an empty virtual filesystem and fills it with files supplied by the generated host code, such as fetched URL assets, inline text or bytes, and tar archives served with the page.

So WebRacket gives the compiled program a virtual filesystem. The next question is how that filesystem gets its initial files. WebRacket populates the VFS by associating VFS paths with contents before the Racket program starts. Those contents can come from host files, fetched URLs, inline text, inline bytes, directories, or tar archives.

That means there are two names to keep separate:

  • The source names where the contents come from outside the WebRacket program, such as a Node host path data/config.txt, a browser URL ./config.txt, inline text, or an archive ./assets.tgz.

  • The VFS path names where those contents appear inside the WebRacket program, such as /app/config.txt or /assets/logo.txt.

The command line creates these associations:

source contents

          |

          v

   WebRacket VFS path

          |

          v

 Racket file and port operations

For example, this command preloads an inline text file:

webracket --node --dest generated --vfs-text /app/message.txt=hello program.rkt
webracket --node --dest generated --vfs-text /app/message.txt=hello program.rkt

Then program.rkt can read the file by its VFS path and print its contents:

"(displayln (file->string \"/app/message.txt\"))"

Running the program prints:

hello

The rest of this chapter follows that order:

  • First, choose how to populate the VFS before the program starts.

  • Then, use ordinary Racket file, path, and port operations on the VFS paths.

  • Finally, keep track of which paths are mutable memory files and which paths are read-only mounts.

5.2 VFS Path Rules🔗

VFS paths use Unix-style slash syntax. Absolute VFS paths start with /. Command-line preload and mount targets must be absolute VFS paths.

  • /app/data.txt is an absolute VFS path.

  • app/data.txt is not accepted as a command-line VFS target.

  • The root directory is /.

  • Relative paths used inside a program are resolved relative to the current VFS directory.

5.4 Preloading Individual Files🔗

Preloading creates ordinary files or directories in the mutable VFS memory backend before the program starts.

5.4.1 Host Files🔗

Use --vfs-file in Node mode to read one host file and preload its contents into one VFS file:

webracket --node --dest generated --vfs-file /app/config.txt=config.txt program.rkt
webracket --node --dest generated --vfs-file /app/config.txt=config.txt program.rkt

Inside the program:

"(displayln (file->string \"/app/config.txt\"))"

If config.txt contains debug=true, the program prints:

debug=true

Host file preloading reads from the filesystem available to the generated Node host module. It is not for browser pages, since browser code cannot freely read local host paths. In browser mode, use --vfs-url for resources that the generated page can fetch.

5.4.2 URLs🔗

Use --vfs-url to fetch a URL into one VFS file. This is primarily useful in browser mode:

webracket --browser --dest generated --vfs-url /app/config.txt=./config.txt program.rkt
webracket --browser --dest generated --vfs-url /app/config.txt=./config.txt program.rkt

The argument has two paths with different meanings. The left side, /app/config.txt, is the absolute VFS path that the WebRacket program will see. The right side, ./config.txt, is a URL source used by the generated host code.

The source URL can be absolute, such as https://example.com/config.txt, or relative, such as ./config.txt. A relative URL is not relative to the Racket source file. It is resolved when the generated host code runs. In browser mode, ./config.txt is fetched relative to the generated .html file, so the asset should be served beside that page. If you use --dest generated, the relative URL is resolved next to the page inside generated/, not next to the Racket source file:

generated/

  out.html

  out.wasm

  config.txt

With those files in the same served directory, ./config.txt names the browser URL next to out.html, while /app/config.txt names the VFS file that the Racket program reads.

In Node mode, --vfs-url also uses fetch, so it can load URLs that Node can fetch, such as https://example.com/config.txt. Local Node files should normally be loaded with --vfs-file instead.

5.4.3 Inline Text🔗

Use --vfs-text for small text fixtures and configuration strings:

webracket --node --dest generated --vfs-text /app/mode.txt=test program.rkt
webracket --node --dest generated --vfs-text /app/mode.txt=test program.rkt

The text is embedded directly in the generated host support file. For example:

"(displayln (file->string \"/app/mode.txt\"))"

prints:

test

5.4.4 Inline Bytes🔗

Use --vfs-base64 for small binary values:

webracket --node --dest generated --vfs-base64 /app/blob.dat=aGVsbG8= program.rkt
webracket --node --dest generated --vfs-base64 /app/blob.dat=aGVsbG8= program.rkt

This option is intended for small data. Large binary assets should normally be loaded from files, URLs, or archives instead.

The example base64 string is hello. Inside the program:

"(displayln (bytes->string/utf-8 (file->bytes \"/app/blob.dat\")))"

prints:

hello

5.4.5 Empty Directories🔗

Use --vfs-mkdir to create an empty VFS directory before the program runs:

webracket --node --dest generated --vfs-mkdir /app/cache program.rkt
webracket --node --dest generated --vfs-mkdir /app/cache program.rkt

Inside the program:

"(displayln (directory-exists? \"/app/cache\"))"

prints:

#t

5.5 Preloading Directories🔗

Use --vfs-dir to copy a host directory tree into the VFS:

webracket --node --dest generated --vfs-dir /assets=assets program.rkt
webracket --node --dest generated --vfs-dir /assets=assets program.rkt

The program can then list and read files under /assets:

"(displayln (map path->string (directory-list \"/assets\")))""\n"
"(displayln (file->string \"/assets/readme.txt\"))"

If the host directory contains readme.txt whose contents are hello assets, the program prints:

(readme.txt)

hello assets

Directory preloading currently loads the directory contents eagerly. In Node mode, the host directory is read by the generated Node host support file. In browser mode, prefer URL or tar archive preloads, since a browser page cannot freely read arbitrary local directories.

5.6 Mounting Tar Archives🔗

A tar archive stores many files in one archive. WebRacket can mount a tar file as a read-only subtree in the VFS.

Use --vfs-tar-file for a host tar file in Node mode:

webracket --node --dest generated --vfs-tar-file /assets=assets.tar program.rkt
webracket --node --dest generated --vfs-tar-file /assets=assets.tar program.rkt

Use --vfs-tar-url for a tar archive fetched by URL:

webracket --browser --dest generated --vfs-tar-url /assets=./assets.tar program.rkt
webracket --browser --dest generated --vfs-tar-url /assets=./assets.tar program.rkt

Inside the program, files in the archive appear under the mount path:

"(displayln (file->string \"/assets/hello.txt\"))""\n"
"(displayln (map path->string (directory-list \"/assets\")))"

If the archive contains hello.txt whose contents are hello archive, the program prints:

hello archive

(hello.txt)

Tar mounts are read-only. You can read files from them, list directories, and copy files out of them. To change data, copy it into a mutable VFS directory or file and write there.

5.7 Mutable Files and Read-Only Mounts🔗

Preloaded individual files, inline text, inline bytes, empty directories, and preloaded directory trees live in the mutable memory backend. A program can write them, replace them, delete them, and create new files next to them.

Tar archives are different. A tar archive is mounted as a read-only backend. The program can read from a tar mount, list its directories, and copy files out of it, but it cannot modify the archive in place.

To modify data from a tar archive, copy it to a mutable path first:

"(copy-file \"/assets/template.txt\" \"/app/template.txt\")""\n"
"(delete-file \"/app/template.txt\")""\n"
"\n"
"(call-with-output-file \"/app/template.txt\"""\n""  "
  "(lambda (out)""\n""    "
    "(display \"updated\" out)))""\n"
"\n"
"(displayln (file->string \"/app/template.txt\"))"

This example copies the read-only template into mutable memory, deletes that mutable copy, and then writes a replacement at the same path. In a real program you can skip the delete step if you only need to copy and read the template.

prints:

updated

The source path /assets/template.txt can be in a tar mount. The destination path /app/template.txt must be in a mutable VFS directory.

5.7.1 Compressed Tar Archives🔗

The same tar options also support gzip-compressed archives. Sources ending in .tar.gz or .tgz are decompressed automatically:

webracket --node --dest generated --vfs-tar-file /assets=assets.tgz program.rkt
webracket --node --dest generated --vfs-tar-file /assets=assets.tgz program.rkt

webracket --browser --dest generated --vfs-tar-url /assets=./assets.tar.gz program.rkt
webracket --browser --dest generated --vfs-tar-url /assets=./assets.tar.gz program.rkt

WebRacket also recognizes gzip data by its magic bytes after loading. This means a downloaded gzip archive can still be handled when its URL does not end in .tar.gz or .tgz.

In browsers, gzip decompression uses DecompressionStream("gzip") when the browser provides it. In Node, gzip decompression uses node:zlib. Decompression failures are reported as WebRacket VFS gzip errors.

5.8 Program Runs and Persistence🔗

The VFS is initialized when the generated host program starts. Each run begins with the preloads and mounts described on the command line.

Writes made by the WebRacket program go into the in-memory VFS for that run. They are visible to later file operations in the same run, but they are not written back to the original host file, URL, or tar archive.

For example, if a program writes /app/out.txt, that file exists inside the VFS while the program is running. It is not automatically saved as a host file beside the generated JavaScript or HTML file.

5.9 Reading Files🔗

Whole-file helpers work on VFS paths:

"(displayln (file->string \"/app/config.txt\"))""\n"
"(write (file->bytes \"/app/blob.dat\"))""\n"
"(newline)""\n"
"(write (file->lines \"/app/lines.txt\"))""\n"
"(newline)""\n"
"(write (file->bytes-lines \"/app/lines.dat\"))""\n"
"(newline)"

For files containing debug=true, hello, and two lines alpha and beta, respectively, this prints:

debug=true

#"hello"

("alpha" "beta")

(#"alpha" #"beta")

Input ports work too:

"(define in (open-input-file \"/app/config.txt\"))""\n"
"(displayln (read-line in))""\n"
"(displayln (read-string 5 in))""\n"
"(displayln (read-byte in))"

For a file containing alpha followed by a newline and then beta, this prints:

alpha

beta

#<eof>

Use port-count-lines! when you want line, column, and position tracking on an input port:

"(define in (open-input-file \"/app/source.txt\"))""\n"
"(port-count-lines! in)""\n"
"(displayln (read-line in))""\n"
"(write (call-with-values (lambda () (port-next-location in)) list))""\n"
"(newline)"

For a file whose first line is first, this prints a location after the first line. The exact column convention follows Racket’s port location tracking:

first

(2 0 7)

Location tracking matters for parsers and readers that report source positions. WebRacket tracks positions on supported input ports, including file-backed input ports.

5.10 Writing Files🔗

The mutable VFS memory backend supports writing through output ports and file helpers:

"(call-with-output-file \"/app/out.txt\"""\n""  "
  "(lambda (out)""\n""    "
    "(display \"hello\" out)))""\n"
"\n"
"(displayln (file->string \"/app/out.txt\"))"

prints:

hello

Common output operations include open-output-file, call-with-output-file, with-output-to-file, display-to-file, and byte/string output procedures such as write-bytes and write-string.

If a path is inside a read-only backend, such as a tar mount, write operations fail. Write to a mutable VFS path instead.

5.11 Directories, Copying, Renaming, and Deleting🔗

The VFS supports common filesystem operations on mutable paths:

"(make-directory \"/app/generated\")""\n"
"(copy-file \"/assets/template.txt\" \"/app/generated/template.txt\")""\n"
"(rename-file-or-directory \"/app/generated/template.txt\"""\n""                          "
                          "\"/app/generated/result.txt\")""\n"
"(displayln (file-exists? \"/app/generated/result.txt\"))""\n"
"(delete-file \"/app/generated/result.txt\")""\n"
"(displayln (file-exists? \"/app/generated/result.txt\"))"

prints:

#t

#f

Copying from a tar mount to a mutable VFS path is allowed because the data is read from the tar backend and written into the memory backend. Renaming or deleting files inside a tar mount is not allowed.

Useful predicates and inspection functions include:

"(displayln (file-exists? \"/app/config.txt\"))""\n"
"(displayln (directory-exists? \"/app\"))""\n"
"(displayln (file-size \"/app/config.txt\"))""\n"
"(displayln (map path->string (directory-list \"/app\")))"

For an /app directory containing config.txt, this prints:

#t

#t

10

(config.txt)

5.13 Backends🔗

Most users do not need to think about backends, but the idea explains why some paths are mutable and others are read-only.

  • Memory backend: The ordinary mutable VFS storage. Preloaded text, base64 data, individual files, created directories, and files written by the program live here.

  • Tar backend: A read-only view of a tar archive. It indexes the archive and serves files from it without turning the archive into mutable files.

  • Synthetic mount directories: Directory entries that connect a mounted backend into the rest of the VFS tree. For example, mounting a tar archive at /assets creates the path /assets so that the archive contents can be reached below it.

This backend model is visible mainly through mutation rules. Files in the memory backend can be changed. Files in a tar backend cannot.

5.14 Limitations🔗

The VFS is designed to make Racket file and port operations useful in WebRacket, but it is not a promise of full operating-system filesystem access.

  • Browser programs cannot read arbitrary local files or directories unless those resources are supplied by the host page, fetched by URL, or embedded in the generated output.

  • Tar mounts are read-only.

  • Large preloads and archives use memory in the JavaScript host and in the WebAssembly runtime. Prefer external files or archives for large assets instead of inline text or base64 data.

  • Not every Racket filesystem procedure is implemented. Consult the implemented primitive list for the current set.

5.15 Common Mistakes🔗

  • Confusing a VFS path with a host path. In /app/config.txt=./config.txt, the left side is the path that the WebRacket program sees. The right side is where the host gets the contents.

  • Expecting a browser build to read a local host path. Browser pages cannot freely open ./data.txt as a filesystem path. Use --vfs-url for browser assets that are served with the generated page.

  • Expecting a relative URL to be relative to the Racket source file. A relative URL such as ./config.txt is resolved by the generated host code when it runs. In browser mode, that means it is relative to the generated .html file.

  • Writing into a tar mount. Tar mounts are read-only. Copy the file to a mutable VFS path before changing it.

  • Expecting VFS writes to update the original host file or archive. VFS writes are visible inside the running WebRacket program, but they are not automatically written back to the host filesystem or URL source.

  • Leaving the compilation target implicit in examples. Use --node or --browser so the reader knows which host environment the command targets.

5.16 Complete Examples🔗

5.16.1 Node: Read a Host File🔗

"read-config.rkt"

"(displayln (file->string \"/app/config.txt\"))"

Compile and run:

webracket --node --run --dest generated --vfs-file /app/config.txt=config.txt read-config.rkt
webracket --node --run --dest generated --vfs-file /app/config.txt=config.txt read-config.rkt

If config.txt contains debug=true, the program prints:

debug=true

5.16.2 Browser: Fetch a Text Asset🔗

"read-message.rkt"

"(displayln (file->string \"/app/message.txt\"))"

Compile for the browser:

webracket --browser --dest generated --vfs-url /app/message.txt=./message.txt read-message.rkt
webracket --browser --dest generated --vfs-url /app/message.txt=./message.txt read-message.rkt

Serve the generated .html, .wasm, and message.txt from the same directory. If message.txt contains hello browser, the program prints:

hello browser

5.16.3 Browser: Mount a Compressed Tar Archive🔗

"read-assets.rkt"

"(displayln (file->string \"/assets/hello.txt\"))"

Compile for the browser:

webracket --browser --dest generated --vfs-tar-url /assets=./assets.tgz read-assets.rkt
webracket --browser --dest generated --vfs-tar-url /assets=./assets.tgz read-assets.rkt

The archive assets.tgz should contain a file named hello.txt. The program reads it as /assets/hello.txt. If that file contains hello archive, the program prints:

hello archive
