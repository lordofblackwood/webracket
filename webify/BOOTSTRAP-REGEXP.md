# Bootstrap Regexp Support

Webify currently has a deliberately small regexp compatibility layer in
`runtime-wasm.rkt`. Its purpose is to let the extracted expander reach startup
milestones before the demodularized regexp library is available in WebRacket.
It is not intended to be a full regexp implementation.

## Implemented Pieces

- `byte-regexp` and `byte-pregexp` construct compact `$Regexp` values from byte
  patterns.
- `regexp?`, `pregexp?`, `byte-regexp?`, and `byte-pregexp?` recognize those
  compact values.
- `regexp-match?` supports a small boolean subset for string and byte inputs:
  literal containment, `[.]`, `[.]zo$`, and `^id(:|$)`.
- `regexp-match` supports only the byte path-list splitter shapes generated by
  `racket/private/path-list`: `#"([^:]*):(.*)"` and `#"([^;]*);(.*)"`.

The path-list support returns the ordinary match-list shape:

```racket
(regexp-match (byte-regexp #"([^:]*):(.*)") #"/a:/b")
;; => '(#"/a:/b" #"/a" #"/b")
```

That is enough for `path-list-string->path-list`, which uses `cadr` and
`caddr` to consume the two captures.

## Why This Exists

The expander startup code reaches a few regexp calls before the full regexp
implementation can be compiled and installed as a library. In particular:

- `racket/private/path-list` uses `byte-regexp` and `regexp-match`.
- Several path/configuration checks use byte regexp predicates such as
  `regexp-match? #rx#"\0" ...`.

Without this bootstrap layer, the expander probe stops at unbound primitive
names before exercising the more interesting module and configuration paths.

## Missing Pieces

- No general regexp parser or matcher.
- No `regexp-match` support for arbitrary character regexps.
- No capture support beyond the path-list byte splitter.
- No `regexp-match-positions`, `regexp-replace*`, ports, events, or other
  regexp APIs.
- No support for the full Racket byte/character regexp contract surface.

## Replacement Direction

The intended replacement is still the demodularized regexp implementation, not
an expanding collection of runtime special cases. New bootstrap cases should be
added only when they unblock expander startup, should be documented here, and
should include a focused probe or `test/test-basics.rkt` case that names the
limited behavior.

Once the demodularized regexp library is available, these runtime bootstrap
helpers should either delegate to it or be reduced to literal constructors and
predicates.
